# 战争迷雾设计与实现协作指南

日期：2026-10-23

本文给 A、C、D、E 说明战争迷雾的产品构思、代码架构、跨组接口和验收方法。它结合了本项目当前 Android 基线、三校区拼图设计、地图定位实现和前几轮讨论结果。

## 1. 为什么做这个功能

最初的想法是：地图上没有探索过的区域使用灰色半透明迷雾遮住；玩家移动时，人物周围一定范围内的地图被侦查并显示；完成一个地标任务后，该地标所在区域整体点亮。这个体验参考了即时战略游戏和开放世界游戏的探索反馈，但在本项目中服务于地标寻宝：玩家要通过移动和观察逐步发现地标，而不是一打开地图就看到全部目标。

战争迷雾必须放在地图页。地标详情页只负责说明任务和进入拍照流程，不能承担探索状态。地图、地标完成状态和拼图奖励共享 `landmarkId`，这样同一个任务完成后可以同时更新地图可见区域和拼图进度。

当前拼图验收基线是北、东、南三个校区各 2×2，共十二块，打卡成功后自动点亮。早期任务表的单张 3×3 拖拽/吸附和摆放恢复描述尚未同步改写，须由管理同学更新；它不是当前战争迷雾 PR 的已通过项。

引导箭头是可选的辅助道具，不是首版必须的自动导航。它可以在玩家卡关、主动请求线索或解开谜语后短暂显示，目标优先选择最近的未完成地标，并受每局次数限制。

## 2. 已确定的玩家规则

### 普通玩家模式

- 未探索区域显示灰色半透明遮罩。
- 当前位置周围的侦查范围用于计算可见区域，但普通模式不显示侦查圈。
- 只有可靠定位才会产生探索记录：当前规则为定位精度不高于 50 米。
- 首次可靠定位立即开雾，之后两个探索中心相距至少 10 米才新增记录，避免定位抖动生成重复孔洞，同时让 15 米侦查视野沿行走轨迹连续。
- 当前默认侦查半径为 15 米；进入地图后地图会聚焦首次定位点。
- 首次定位精度不足时，仍即时显示人物附近的临时视野，但不保存为历史探索；信号中断后临时视野消失。
- 进入侦查范围后，地标和地图细节自然显现。
- 完成地标后驱散其所在的整块区域。当前演示打卡可触发该效果；正式版必须等服务端打卡成功后才更新。
- 拍照取消、上传失败、定位精度不足或重复请求不能提前驱散迷雾。

### Debug 模式

Debug 包的地图页可以：

- 临时显示全图，关闭迷雾；
- 显示或隐藏侦查圈；
- 调整当前地标的打卡范围半径；
- 在圆形和矩形范围之间切换；
- 直接标记当前地标完成，检查区域驱散。

Debug 状态只在当前进程有效，Release 包不显示入口，不改变正式玩家数据。

### 引导规则

第一阶段只设计接口和手动触发，不加入自动卡关计时。后续可以选择：

1. 每局固定 3 次“显示线索”；
2. 玩家卡关一段时间后获得一次提示；
3. 服务端下发谜语，回答正确后获得一次 `GuideGrant`。

无论采用哪种方式，客户端都不能保存正确答案，也不能自行增加次数。引导目标从未完成地标中选择最近者，并显示方向、距离和剩余次数。

## 3. 当前代码架构

数据流如下：

```text
LocationProvider
    -> MapViewModel
    -> MapUiState.exploredCenters / completedLandmarkIds
    -> MapRenderState
    -> AmapMapAdapter 或 DemoMapContent
```

关键代码位置：

- `core/location/AmapLocationProvider.kt`：高德定位流和定位精度。
- `feature/map/MapViewModel.kt`：可靠定位过滤、10 米探索中心记录、完成状态订阅和 Debug 状态。
- `core/model/CampusRevealBlocks.kt`：按每校区四个地标生成四块临时多边形，稳定绑定地标与碎片索引。
- `feature/map/MapContract.kt`：`MapUiState`、`MapAction`、`MapRenderState`。
- `core/map/AmapMapAdapter.kt`：真实高德地图的灰色 Polygon 和孔洞。
- `feature/map/DemoMapContent.kt`：离线演示地图的灰色遮罩和透明孔洞。
- `app/ExplorationProgressStore.kt`：当前演示版的进程内完成地标状态。
- `feature/checkin/CheckInResultScreen.kt`：演示打卡结果携带地标 ID 并写入完成状态。
- `docs/adr/0002-campus-puzzle-reveal.md`：十二个地标、三校区和拼图碎片关系。
- `docs/adr/0003-map-fog-of-war-and-guidance.md`：战争迷雾和引导的架构决策。

真实地图使用一个覆盖全图的灰色多边形：历史探索中心和当前临时视野用 `CircleHoleOptions` 挖出 15 米可见孔洞，已完成地标用 `PolygonHoleOptions` 挖出整块区域。离线演示地图使用同一组历史中心、临时视野和分块多边形，并将地理坐标投影到画布；低精度当前位置只能打开临时孔洞，不计入永久进度。

用户提供的学校官方良乡校区 PDF 确认了北、东、南片区及建筑相对位置，但不含可直接转换为 GCJ-02 的配准控制点。现阶段每区四块以演示地标为锚点生成临时分区，保证每个地标落在自己的块内；这不是官方精确地图边界。实测十二个地标后，B 与 A 再按官方图和道路边界冻结正式多边形。

## 4. 各成员需要做什么

### B：地图、定位和客户端状态

已完成或已实现：

- 地图页战争迷雾，而不是详情页迷雾；
- 普通模式隐藏侦查圈，Debug 模式可显示；
- 可靠定位记录探索中心；
- 完成地标扩大可见区域；
- Debug 地图面板；
- 定位首个结果和后续信号的 12 秒看门超时提示；
- 本机 `testDebugUnitTest`、`assembleDebug`、`lintDebug` 通过。

仍需 B 配合完成：

- 将 C 的真实完成事件接入地图状态；
- 将 D 的持久化进度接入 `ExplorationProgressStore` 替代层；
- 接入手机朝向，计算引导箭头方向；
- 真机确认低精度、无定位和系统定位关闭时不误判。

### A：视觉和交互规范

- 确定迷雾颜色、透明度、地标遮挡层级和完成区域反馈；
- 设计 Debug 控件的视觉边界；
- 设计箭头、目标标记、剩余次数和谜语提示；
- 检查迷雾不会遮挡必要的地图操作和错误提示；
- 做陌生用户走查，确认用户理解“已探索、可见、已完成”的区别。

### C：真实拍照和完成事件

- 接入 CameraX、权限、拍照、重拍和方向修正；
- 用 Room 或明确的草稿 Repository 保存照片文件和状态；
- 上传成功后携带真实 `landmarkId` 和 `photoId`；
- 只有服务端打卡成功后发出完成事件；
- 取消、失败、重复提交不能触发驱散；
- 已完成地标状态供地图和引导模块过滤。

建议的客户端事件语义：

```text
PhotoConfirmed
    -> UploadSucceeded(photoId)
    -> CheckInSucceeded(checkInId, landmarkId, fragmentId)
    -> ProgressStore.markLandmarkCompleted(landmarkId)
    -> MapViewModel 增加完成区域孔洞
```

### D：进度、打卡和引导服务

当前正式 OpenAPI 只有 `/health`；业务请求模板不能当作已完成接口。D 需要：

- 地标列表和详情；
- 照片上传和归属校验；
- 幂等打卡、碎片发放和审计；
- 探索中心和已完成地标的保存/恢复；
- 拼图进度；
- 引导次数、谜语挑战和一次性授权。

建议进度结构：

```json
{
  "levelId": "liangxiang-2026",
  "exploredCenters": [
    {"latitude": 39.72, "longitude": 116.14}
  ],
  "completedLandmarkIds": ["north-lake"],
  "version": 4,
  "updatedAt": "2026-10-23T10:00:00.000Z"
}
```

更新接口必须幂等，重复同步不能重复创建探索记录。引导接口可采用：

```text
POST /api/v1/guides/challenges
POST /api/v1/guides/challenges/{challengeId}/answer
    -> GuideGrant(targetLandmarkId, bearingDegrees, distanceMeters, expiresAt)
```

服务端保存答案和消费记录，客户端只展示获准的箭头数据。

### E：设备、回归和发布证据

- 两品牌手机验证普通模式无侦查圈；
- 移动后侦查范围内地图变亮；
- 完成地标后对应区域扩大可见；
- 无定位、低精度、权限拒绝、后台和进程重启不误驱散；
- Debug 开关只在 Debug 包可见；
- 记录 Commit、APK SHA-256、设备、系统版本、截图和录屏；
- 在 `acceptance-report.md` 中增加战争迷雾专门验收项。

## 5. 推荐实现顺序

### 阶段一：客户端可视化基线

B 完成迷雾遮罩、探索中心、完成区域、离线演示和 Debug 面板。当前代码已经达到这一阶段，并完成本机编译验证。

### 阶段二：真实完成事件

C 先完成真实拍照和草稿，再与 D 的上传/打卡接口联调。地图只订阅“打卡成功”的完成事件，不监听“拍照按钮点击”。

### 阶段三：进度持久化

D 提供探索进度和完成地标接口；客户端把当前进程内 Store 替换为持久化实现。需要处理重复同步、网络失败和版本冲突。

### 阶段四：引导箭头

B 接入手机朝向和箭头绘制，D 提供次数/谜语授权，A 验收视觉。先做手动有限次数提示，再决定是否加入自动卡关计时。

### 阶段五：真机和校园步行验收

E 组织两品牌手机在真实校区步行，记录定位精度、迷雾显示、完成驱散、断网、后台和重启结果。坐标和打卡范围必须实地核验，当前目录演示坐标不能直接用于正式开放。

## 6. 验收清单

- [ ] 普通模式未探索区域被灰色半透明遮罩覆盖。
- [ ] 普通模式不显示侦查圈，Debug 模式可显示。
- [ ] 首次可靠定位立即开雾；后续间隔不足 10 米时不会产生重复探索中心。
- [ ] 侦查孔洞半径约 15 米，沿步行轨迹连续。
- [ ] 完成地标后只驱散其所属整块区域，每区仍为四块。
- [ ] 低于 50 米精度阈值的定位才会探索区域。
- [ ] 首次定位 12 秒无结果时显示可恢复提示。
- [ ] 定位信号中断时保留上次位置，不伪造新探索区域。
- [ ] 拍照取消、上传失败和重复请求不会驱散迷雾。
- [ ] 服务端打卡成功后只驱散对应地标区域。
- [ ] 应用重启后探索和完成状态可以恢复。
- [ ] 引导目标不会选择已完成地标，次数和授权由服务端控制。
- [ ] 两台不同品牌设备结果一致，并有截图/录屏/日志证据。
