# 相机闭环整改 · 第三轮复核回复（F1~F3）

日期：2026-11-04。对应 E 对 `f5228b4` 的第二轮复核意见（`PR10_C第二轮复核_f5228b4_2026-11-04.md`），结论「主要整改有效，还剩 F1/F2 客户端边界 + F3 的 C/D 终态语义」。

## 逐项整改

### F1 / P1：UNKNOWN 恢复不再依赖本地照片

| 问题 | 修复 |
|---|---|
| `recoverDraft` 仅在照片文件存在时才写回 `uploadState`，缺照时 UI 回退 EMPTY、未知保护失效 | 抽 `CheckInFlowRules.buildRecoveredDraftPatch`：**无条件**恢复 `uploadState`；照片缺失仅把 `photoPath` 置 null（预览不可用），`markRequestSent` 仍按 `UNKNOWN` 置位 |
| `submitFlow` 先 `photoPath ?: return` 再判 `requestSent`，缺照时到不了 `recoverAttempt` | 改为 `CheckInFlowRules.submitRoute`：先「已发出/未知 → RECOVER」，再「明确失败 → NEW_ATTEMPT」，最后才 FIRST_SUBMIT（此时才检查照片） |
| 缺照 UNKNOWN 页面无「恢复结果」入口（显示拍摄入口） | `ActionButtons` 新增 `isOutcomeUnknown` 分支，仅显示「重试恢复」，不显示拍照/重拍 |

### F2 / P2：重拍进入预览与「采用新照片/新尝试」分离

| 问题 | 修复 |
|---|---|
| FAILED 点 Retake 立即 `beginNewAttempt`，删除旧照，取消重拍无法回旧预览 | `retake()` 不再对 FAILED 调 `beginNewAttempt`，统一走 `CheckInAttemptRules.canRetake`（仅切预览、保留旧照与当前 attempt） |
| 新请求可能复用旧 key | 拆出 `resetAttemptContext()`（仅生成新 `att_<uuid>` + 清 challenge/photo/location/requestSent，**不删旧照、不改 uploadState**）；`capture()` 仅在 `requestSent`（旧尝试已发出）时先重置上下文，新照成功才替换旧照 |

### F3 / P1（C/D 协作）：NotFound 终态语义统一

| 问题 | 修复 |
|---|---|
| `recover` 对 NotFound 无条件返回 `CONFIRMED_ABSENT`，与 `onUnknownOutcome` 的「保持未知」矛盾；页面据此删旧照、换新 ID | `CheckInSubmitCoordinator.recover` 对 `NotFound` 改为 `unknownResult = true`（保持 `UNKNOWN`），与 `onUnknownOutcome` 一致。终态保证成立前不放开新尝试 |
| 文档「服务端保证成立前保持未知」与代码不一致 | `docs/api/checkin-recovery.md` 更新为 F3 定稿：NotFound 仅「此刻未查到」，在 D 交付「可靠终态 + 在途 POST 竞态测试」前一律保持未知；明确拒绝（CHALLENGE_EXPIRED/IDEMPOTENCY_CONFLICT）才可 CONFIRMED_ABSENT；新增 D 待办第 5 项 |

> 说明：`onChallengeExpired` / `onIdempotencyConflict` 中 NotFound → CONFIRMED_ABSENT 保留不变——这两条是**服务端已明确拒绝**（明确 4xx）后的查询确认，不存在「在途 POST 晚到」竞态。
