# 相机闭环整改 · 第五轮复核回复（C-4 候选尝试 + 新 ID 修复）

日期：2026-11-07。对应「拍摄失败仍覆盖旧上下文」「换 ID 时机与 D 新契约不兼容」两项意见，及随后补报的「明确失败→重新开始复用旧 ID」入口问题。

## 逐项整改

### 问题 1：拍摄失败仍覆盖旧上下文

| 问题 | 修复 |
|---|---|
| `capture` 在拍摄前就 `frozenLocation = location`、领新 challenge 并 `persistDraft` 覆盖草稿；CameraX 失败后仅置 `isCapturing=false`，不回滚，旧 challenge/定位丢失 | 引入「候选尝试」：领 challenge / 更新定位只发生在候选内，**不落正式字段、不覆盖草稿**；拍摄成功 `commit` 才采用（attemptId + challenge + 定位 + 照片），失败/取消 `abort` 丢弃候选，`challenge_old` / 旧定位 / 旧照片 / 旧 attempt 全部保留 |

### 问题 2：换 ID 时机与 D 新契约不兼容

| 问题 | 修复 |
|---|---|
| D 要求 challenge **拍前**绑定 attempt；C 此前在 `onCaptured`（新照片成功后）才 `rotateAttemptId()`。简单合并会「challenge 绑旧 ID、上传用新 ID」 | `createChallenge` 增加 `attemptId` 参数，challenge 拍前即绑定候选 attemptId；仅 `requestSent=true`（已发送过的 attempt 不可复用）才生成新候选 ID，拍摄成功 `commit` 后 attempt 与 challenge 一致采用 |

### 问题 3：已发送明确失败 → 重新开始 → 再次拍摄复用旧 ID

| 问题 | 修复 |
|---|---|
| `beginNewAttempt` 调 `resetAttemptContext` 清了 `requestSent` 却未生成新 ID；候选随后见 `requestSent=false` 复用旧 ID，challenge/上传/POST 全程旧 ID，触发 D 幂等冲突 | 在「可靠结束旧尝试」时刻（`resetAttemptContext`）**原子生成新 attemptId**（对应纯规则 `CheckInCandidateRules.resetForNewAttempt`）；后续 capture 复用该新 ID 领新 challenge，challenge/上传/POST 全程同一新 ID |

> 「直接点重拍」路径不受影响、无需重做：该路径 `requestSent` 未被清除，候选仍按 `needsNewAttemptId(requestSent=true)` 生成新 ID。

## 候选尝试规则（`core/checkin/CheckInCandidateRules.kt`）

| 场景 | 候选 attemptId | 候选 challenge |
|---|---|---|
| `requestSent=true`（已发送需换新） | 新生成 `att_<uuid>` | 新领，绑定新 ID |
| 可靠结束旧尝试（`resetForNewAttempt`） | 新生成 `att_<uuid>` | 空（capture 复用此 ID 领新 challenge） |
| `!hasValidChallenge`（首拍 / 挑战过期） | 复用官方 attemptId | 新领，绑定官方 ID |
| 挑战有效（重拍仅换照片） | 复用官方 attemptId | 复用官方 challenge |

`commit` 把候选提升为官方上下文；`abort` 丢弃候选、官方不变。均有纯规则单测覆盖。

- `capture` 候选流程与 `resetAttemptContext` 是 ViewModel 层接线，其决策语义由纯规则 `CheckInCandidateRules` 单测锁定；真实 `CameraViewModel`/Compose 集成单测仍 NOT_RUN（Android 耦合，沿用既有边界）。
- 照片上传绑定 challenge（D-3）仍为服务端待办，本轮未改客户端 `uploadPhoto`。
