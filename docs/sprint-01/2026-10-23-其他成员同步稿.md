## 二、需要其他成员继续完成的内容

### A：产品流程、UI/UX 和用户验收

**需要完成**

- 确认地图页战争迷雾的灰色透明度、地标在迷雾内外的显示层级和可读性。
- 确认 Debug 面板、侦查圈、范围形状切换和完成地标后的视觉反馈；Debug 控件只存在 Debug 包。
- 设计引导箭头、目标标记、按钮和动画的视觉规范。箭头是辅助道具，不能替代玩家探索。
- 与 C 一起确认相机页、重拍、取消、照片确认和打卡结果页的交互。
- 与产品流程一起检查陌生用户能否完成“地图→地标→拍照→打卡→获得碎片→拼图”的闭环。

**创作背景**

战争迷雾是地图页的探索反馈，不应放到地标详情页。玩家移动时，当前位置周围逐步显示地图；完成地标后扩大该区域的可见范围。B 已完成主要计算和绘制，但透明度、信息层级、箭头是否易懂需要 A 站在玩家视角验收，否则功能虽然能运行，玩家可能不知道哪里已探索、哪里可打卡、引导是否消耗次数。

**验收证据**

`S1-MAP-01`、`S1-UX-01`，以及地图和相机流程的截图/录屏、陌生用户观察记录。

### C：CameraX、照片草稿、上传协作和拼图

**需要完成**

- 接入真实 CameraX 预览、拍照、重拍、取消和 `CAMERA` 权限处理。
- 保存真实照片文件和草稿元数据，支持从相机返回、后台切换和进程被杀后恢复；不能只在内存中保存 Bitmap 或模拟照片。
- 确认照片方向、压缩、临时文件清理和无照片时的错误提示。
- 与 D 对接照片上传，成功得到 `photoId`；上传失败可重试，不重复创建打卡记录。
- 按 ADR 0002 完成三个校区各 2×2 碎片的自动点亮和完成反馈；旧表中的拖拽、吸附和摆放恢复须先由管理同学决定是否另立扩展任务。
- 拍照确认成功后发出真实的 `landmarkId` 和完成事件，使地图驱散对应区域，并让引导目标排除已完成地标。

**创作背景**

当前 B 侧相机导航和结果页已经有路由骨架，但拍照仍是模拟流程，演示状态由应用内存保存。战争迷雾完成区域的驱散需要真实的地标完成事件；如果 C 不提供照片草稿和完成事件，B 的 `S1-B-05`、`S1-B-06` 只能停留在演示链路，应用重启后也无法恢复。

**验收证据**

`S1-CAM-01`、`S1-DRAFT-01`、修订后的 `S1-PUZZLE-01`，并与 D 共同完成 `S1-UPLOAD-01`。旧 `S1-PUZZLE-02` 的拖拽摆放恢复标准须重新定范围。需要拍照录屏、样图、强杀进程前后截图、上传请求和错误重试记录。

### D：业务 API、CloudBase、进度同步和幂等

**需要完成**

- 在现有 `/health` 之外，定稿并实现地标列表/详情、照片上传、打卡提交、重复打卡、探索进度、拼图进度和奖励接口。
- 明确 `Landmark`、`CacheTask`、`CheckInRecord`、`PuzzleProgress`、照片和探索中心的数据字段、分页方式、定位单位、精度阈值和距离判定。
- 定稿业务错误码：未登录、定位不准、距离过远、重复打卡、上传失败、限流和服务端异常；客户端按错误码决定提示和重试。
- 打卡接口必须幂等：同一个请求重试不能重复发放拼图碎片或奖励，服务端保存唯一打卡记录。
- 保存 `completedLandmarkIds`、探索中心、拼图进度和引导剩余次数；当前客户端的 `ExplorationProgressStore` 只在进程内有效，正式版本需要本地持久化或服务端同步。
- 设计谜语引导接口：服务端返回 `HintChallenge`，答案校验成功后生成一次性的 `GuideGrant`；答案不能保存在客户端。
- 提供本地/测试环境可复现的 CloudBase 部署和 API 回归数据。

**创作背景**

当前仓库的 OpenAPI 只正式定义了 `/health`，地标、打卡、进度等 Bruno 请求只是模板，不能作为业务接口已通过的证据。B 的真实主流程依赖 C 的照片和 D 的上传、打卡、奖励、进度接口；没有 D 的契约和幂等保证，无法验收“上传→打卡→发碎片→拼图”的完整闭环，也无法让战争迷雾和引导跨进程、跨设备保存。

**验收证据**

`S1-API-01`、`S1-UPLOAD-01`、`S1-IDEMP-01`，以及地标/进度/打卡的 OpenAPI、CloudBase 日志、请求响应和三次重复请求只生成一条记录的数据库证据。

### E：测试、集成、CI 和发布验收

如果 E 由你负责，则需要继续补齐以下证据；如果由另一位同学负责，应把任务明确分派给该同学。

- GitHub CI 工作流及至少一次成功运行记录。
- 非作者 Review、分支保护和 PR 合并顺序记录。
- 第二台电脑从干净仓库构建的命令、版本、Commit 和日志。
- 两台不同 Android 真机的安装、启动、定位、相机和主流程证据。
- 真实云端回归，不把本地 `/health` 或 Debug APK 构建当成云端验收。
- 缺陷编号、P0/P1 分级、复测结果和关闭证据，尤其是表中引用但未展开的 `S1-E-14`。
- 更新 `docs/sprint-01/acceptance-report.md`，填写每项负责人、Commit、设备、日期、结果、证据和已知问题。

**创作背景**

本项目的风险不只是代码能否编译，还包括真实地图 Key、定位精度、相机权限、进程恢复、云端部署和重复请求一致性。现有本机 Android 验证已通过，但没有设备和非作者证据时，不能把整项验收标成 PASS。
