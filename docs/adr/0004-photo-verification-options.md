# 打卡照片核验方案

日期：2026-10-29（2026-10-30、2026-11-01 补充拍板细节）
状态：Accepted（团队拍板）

## 1. 决策总纲

采用「**到达范围后开放拍照 + 服务端综合校验**」：

- 用户只有**进入地标打卡范围**且**定位精度合格（≤30m）**后，才能打开 CameraX 拍照；客户端**不允许从相册选图**。
- 照片上传后由**服务端**综合复核：位置仍在有效范围、一次性挑战码未过期、服务器接收时间合理。
- **人脸存在性由客户端 ML Kit 初检承担**；首版服务端**不做人脸复核**（2026-11-01 拍板，留作后续加分项 / 可选）。
- 人脸检测只证明「确实有人参与拍摄」，**不单独证明是本人**；确认身份需额外人脸比对并取得隐私授权。
- 建筑识别仅作**辅助评分 / 风险提示 / 人工复核依据**，不作为首版硬性条件，也不替代地理范围与服务端校验。

## 2. 核验手段定位

| 手段 | 定位 | 是否硬性 | 说明 |
|------|------|----------|------|
| 地理围栏 | 拍照前置门槛 + 服务端复核 | 硬性（双重） | 进范围 + 精度 ≤30m 才开放拍照；服务端再次校验 |
| 一次性挑战码 | 服务端时效校验 | 硬性 | 绑定 userId+landmarkId+photoId，未过期且未消费才可提交 |
| 服务器接收时间 | 服务端合理性校验 | 硬性 | 接收时间与拍摄时间 / 挑战码窗口比对 |
| 人脸检测 | 「确实有人参与拍摄」校验 | 客户端硬性 / 服务端首版不做 | 客户端 ML Kit 初检承担；服务端复核首版不做（留后续）；不能证明本人 |
| EXIF 时间 | 辅助证据 | 辅助 | 可被修改，不单独信任 |
| 建筑识别 | 辅助评分 / 风险提示 / 人工复核 | 非硬性 | 光照/季节/遮挡/角度/相似楼体影响大，12 地标标注维护成本高，误拒率高 |

## 3. 最终流程

```text
进入范围（≤30m 且精度合格）
  -> 显示取景引导
  -> 拍照（CameraX，禁止相册选图）
  -> 人脸 / 照片质量初检（客户端 ML Kit）
  -> 上传照片
  -> 服务端复核：位置 + 挑战码 + 时间
  -> 通过后发放碎片
```

## 4. 客户端 / 服务端职责划分

### 4.1 客户端（组员 C）

1. **门控**：进入围栏 + 精度 ≤30m 才解锁「拍照」入口；未达标时禁用并提示（复用 `isReliableForCheckIn` + 距离 ≤ 围栏半径判断）。
2. **取景引导**：拍照页显示引导提示（如「请面向地标，将人物置于画面中」）。
3. **拍照后初检**：本地检测「照片中有清晰人脸、数量符合要求、尺寸和亮度合格」，不合格提示重拍；**不做人脸身份识别**。选型见 §5。
4. **上传链路**：`POST /checkin-photos` 拿 `photoId` → 领 challenge（带 landmarkId + photoId）→ `POST /checkins`（Idempotency-Key）拿 `CheckInReceipt`，`UploadState` 完整流转 `CAPTURED → UPLOADING → UPLOADED → CONFIRMED`，失败落 `FAILED` 可重试。

### 4.2 服务端（D 组）

1. **位置**：仍在有效范围 + 精度 ≤30m（`geo.ts` 由 50m 改 30m）。
2. **挑战码**：补 `consumed` 一次性消费语义，绑定 `userId + landmarkId + photoId`，有效期仍 5 分钟；在同一数据库事务内完成「校验挑战码 → 标记已消费 → 创建打卡记录」，重复提交返回幂等结果，不重复发奖 / 消费。
3. **时间**：服务器接收时间合理（新增，阈值与挑战码 TTL 联动）。
4. **人脸**：**首版服务端不做人脸复核**（2026-11-01 拍板）。人脸存在性由客户端 ML Kit 初检承担；服务端人脸复核留作后续加分项 / 可选（需要时再选腾讯云 API / face-api.js 等，届时抽象成可替换接口）。
5. **EXIF 时间**：辅助证据（新增，读照片 `DateTimeOriginal`，不单独作为判据）。

## 5. 人脸检测客户端选型调研结论（2026-10-30）

需求：首版只做「人脸存在性 + 数量 + 尺寸 + 亮度 + 清晰度」初检，不做身份识别；要求离线、免费、对无 GMS 的国产 Android 设备可用、Compose/CameraX 集成友好。

| 方案 | 离线 | 授权成本 | 准确率 | 依赖 | 结论 |
|------|------|----------|--------|------|------|
| **ML Kit 捆绑版** `com.google.mlkit:face-detection:16.1.7` | ✅ 模型打进 APK（约 2–5MB） | 免费 | 高（深度学习） | **无 GMS 依赖**，适配国产设备 | **首选** |
| ML Kit Play 服务版 | ⚠️ 首用需下载 | 免费 | 高 | **依赖 GMS**，国内设备不可用 | 弃用 |
| OpenCV Haar/LBP | ✅ 完全离线 | 免费 | 中（侧脸/暗光误检高） | 无，但需自调参 | 降级备选 |
| 商业 SDK（虹软/百度/腾讯移动端） | 部分离线 | 付费/需授权 | 高（带活体） | 厂商 key | 课程作业不划算，弃用 |
| TFLite 自研模型 | ✅ | 免费 | 取决于模型 | 需训练/优化 | 过度设计，弃用 |

**结论：采用 ML Kit「捆绑版」（bundled）**，关键点是用 `com.google.mlkit:face-detection` 而非 `com.google.android.gms:play-services-mlkit-face-detection`——后者依赖 Google Play 服务，国内设备无法使用。客户端初检已实现（`core/camera/FaceQualityChecker.kt`，commit 28ee338）。

**配套说明**：ML Kit 直接给出「人脸存在 + 数量 + bounding box（尺寸/位置）」；「亮度」与「清晰度」需少量补充逻辑（亮度取 Bitmap 平均亮度，清晰度可用拉普拉斯方差），不引入额外重型库。若个别机型 ML Kit 异常，再降级 OpenCV Haar 兜底。

**ML Kit 平台边界（重要）**：ML Kit Face Detection 是 **Android 客户端 SDK，无法在服务端（Node.js 云函数）运行**。因此服务端人脸复核不能选 ML Kit，只能选服务端方案（腾讯云 API / face-api.js 等），本 ADR 已决定首版不做服务端人脸复核。

## 7. 影响与边界

- **核验主体在服务端**：客户端只负责采集、门控与初检，最终发放以服务端复核（位置 + 挑战码 + 时间）为准。
- **人脸 ≠ 本人**：人脸检测仅证「有人参与拍摄」；如需确认身份，须引入人脸比对并取得隐私授权。
- **建筑识别不替代校验**：仅作风险提示或人工复核依据，不作为硬性门槛。
- **精度口径已统一 30m**：客户端 `GeoMath.kt`（`MAX_CHECK_IN_ACCURACY_METERS` 50f→30f）与服务端 `geo.ts`（`validateLocationAccuracy`）正式打卡门控统一为 30m；战争迷雾探索保持 `FogOfWarRules.MAX_EXPLORATION_ACCURACY_METERS = 50f` 不变，两者不混用。
- 本方案客户端改动集中在 `CameraScreen` / 相机入口 / 新增上传 Repository 与初检模块；服务端改动集中在 `checkins.ts` / `photos.ts` / `challenges.ts` / `geo.ts`。
