## 为什么手机仍显示旧坐标

联机 Debug APK 的 `HAS_AMAP_KEY` 和 `HAS_CLOUD_API` 均为 `true`。地图页通过 `CloudBaseLandmarkRepository` 请求线上 `/api/v1/landmarks`，不会使用 APK 中的 `LiangxiangTreasureCatalog` 作为联网失败后的静默回退。因此只换 APK 不会改变线上地标位置。

2026-11-10 通过现有数据库 REST 凭据**只读查询**了 12 个 active 地标，全部仍为 2026-10-25 旧种子坐标；与新候选点相差约 119–536 米。例如：

| ID | 线上旧 GCJ-02 | 提交中的新 GCJ-02 |
|---|---|---|
| `lmk_north_lake` | 39.736600, 116.166600 | 39.734016, 116.168918 |
| `lmk_north_library` | 39.733500, 116.164900 | 39.730967, 116.170264 |
| `lmk_east_qinyuan` | 39.736800, 116.174300 | 39.734800, 116.176863 |

完整 12 点、采样/OSM 对象来源和转换说明见 [坐标整合记录](2026-11-10-良乡地标坐标整合记录.md)。最终数据分别在 Android 本地目录、[canonical fixture](../api/fixtures/campus-catalog.json) 和 [增量迁移](../../cloudbase/migrations/20261110180000_update_liangxiang_landmark_coordinates.sql) 中；CloudBase 契约测试会检查三者数值一致。

## D 的执行步骤

1. 从 GitHub 拉取 `integration/c-camera-cloudbase`，确认包含 `7432d35`。与 B/A 确认这 12 个点是**本轮测试候选中心**，尤其北湖湖岸拍摄点未定；确定要更新的 CloudBase 环境 ID，不能误操作其他环境。
2. 在目标环境先导出 `landmarks` 中这 12 个 ID 的 `id,latitude,longitude,coordinate_system,coordinate_verified,check_in_area,status`，备份文件留在私有位置，不提交 Git。可执行只读 SQL：

   ```sql
   SELECT id, latitude, longitude, coordinate_system,
          coordinate_verified, check_in_area, status
   FROM landmarks
   WHERE id IN (
     'lmk_north_lake', 'lmk_north_zongjiao',
     'lmk_north_student_service', 'lmk_north_library',
     'lmk_east_gantang', 'lmk_east_qinyuan',
     'lmk_east_wencui', 'lmk_east_wenbo',
     'lmk_south_shutong', 'lmk_south_boya',
     'lmk_south_lijiao', 'lmk_south_industrial_ecology'
   ) ORDER BY id;
   ```

3. 使用已登录且有权限的 CloudBase SQL 控制台或 CLI，在**同一个目标环境**执行迁移文件 `cloudbase/migrations/20261110180000_update_liangxiang_landmark_coordinates.sql`。若使用 CLI，先完成 `tcb` 登录并设置本机私有 `CLOUDBASE_ENV_ID`，再从仓库根目录运行：

   ```powershell
   $sql = Get-Content -Raw cloudbase/migrations/20261110180000_update_liangxiang_landmark_coordinates.sql
   node node_modules/@cloudbase/cli/dist/standalone/cli.js db execute -e $env:CLOUDBASE_ENV_ID --sql $sql --json
   ```

   当前仓库的 `npm run deploy` 只部署云函数，**不会替你执行 SQL 迁移**。如果 CLI 不支持该环境的多语句执行，改用 SQL 控制台执行完整文件并检查事务结果；不要按行人工复制部分值。
4. 再次执行第 2 步查询，确认 12 行均存在，坐标与 canonical fixture 逐项一致，`coordinate_system='GCJ02'`。迁移不改 `coordinate_verified`、打卡范围、分区、碎片 ID 或任务 ID。
5. 用真实玩家接口 `GET /api/v1/landmarks` 核查返回仍为 12 个 active 地标，且至少北湖、图书馆、勤园的值与上表右列一致；再在手机上关闭并重开地图页，确认标记移动。记录环境 ID、迁移时间、线上查询结果、APK/提交 SHA 和截图供 E 复核。

## 回滚

若线上 API 返回异常、地标数不是 12，或地图标记明显偏离，应停止继续测试，依据第 2 步私有备份中的原值回滚这 12 行，并再次查询确认。当前只读快照保存于执行者电脑的临时目录，不应依赖其他人的本机路径。不要回滚整张表或重新运行旧种子迁移；旧种子包含其他契约字段的 upsert，可能覆盖新版本数据。

## 仍未关闭的风险

- 北湖采用 [OSM 北湖水体](https://www.openstreetmap.org/way/298568789) 的几何中心。该水体约 340 米长，中心附近原有 55 米打卡圈可能只覆盖水面；必须现场另选可通行湖岸拍摄点，再调整打卡区域。
- OSM 建筑中心和人工外圈均不等于安全拍照站位；`coordinate_verified=false` 应保持不变，不能将迁移成功写成 12 点现场验收通过。
- OSM 候选值由 WGS-84 转为 GCJ-02。正式产品使用 OSM 派生数据时，应在 App 可见的许可/致谢入口注明 OpenStreetMap contributors 与 ODbL，详见 [OSM 版权要求](https://www.openstreetmap.org/copyright)。
- 本机到线上 `LIVE_API_BASE/health` 仍出现连接异常，但数据库 REST 只读查询可用。D 应分别检查 API 网关与数据库 REST；数据库更新成功不自动证明玩家接口或手机网络可用。
